# T-005: Supabase Row Level Security (RLS) & Security Tests

## 1. Goal
Implement strict PostgreSQL Row Level Security (RLS) policies on `profiles` and `resumes` tables, accompanied by a comprehensive test suite written by QA proving complete multi-tenant isolation and zero cross-tenant data leakage.

## 2. Owner Role & Test Author
- **Owner Role:** Database & Security Engineer
- **Test Author:** QA Engineer (QA writes `tests/rls.test.ts` *before* RLS policies are finalized)

## 3. Allowed Files
- `supabase/migrations/20261018000003_resumes_rls.sql` (RLS policies)
- `tests/rls.test.ts` (security test suite verifying isolation under multiple tenant contexts)

## 4. Human-Only Prerequisites
- Human review and approval of all RLS policy definitions prior to migration application.

## 5. New Dependencies for Human Approval
- None.

## 6. Dependencies
- T-004 (Core database tables and triggers)

## 7. Acceptance Criteria
1. **Enable RLS:**
   ```sql
   alter table profiles enable row level security;
   alter table resumes enable row level security;
   ```
2. **`profiles` Security Policies:**
   - `read_own_profile`: `for select using (id = auth.uid());`
   - `update_own_profile`: `for update using (id = auth.uid()) with check (id = auth.uid());`
3. **`resumes` Security Policies:**
   - `own_resumes_all`: `for all using (user_id = auth.uid()) with check (user_id = auth.uid());`
   - Blocks unauthorized access to `select`, `insert`, `update`, and `delete`.
4. **Service Role Access:** Service role retains administrative bypass for backend batch processes and webhooks.
5. **QA Automated Security Test Suite (`tests/rls.test.ts`):**
   - QA engineer authors test suite prior to implementation using local Supabase clients authenticated as:
     - User A (`tenant-a`)
     - User B (`tenant-b`)
     - Anonymous client (unauthenticated)
   - Asserts:
     - **Cross-tenant SELECT:** User A cannot query or read resumes created by User B (returns 0 rows).
     - **Cross-tenant UPDATE:** User A cannot modify any field of User B's resume (returns 0 rows affected).
     - **Cross-tenant DELETE:** User A cannot delete User B's resume (returns 0 rows affected).
     - **Impersonated INSERT:** User A cannot insert a resume with `user_id = User B.id` (rejected by RLS check).
     - **Anonymous Access:** Unauthenticated requests cannot read, insert, update, or delete any resume records.
   - All assertions pass with 100% green status.
