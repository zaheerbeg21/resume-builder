# T-026: User Account Deletion & Cascade Data Erasure (GDPR Art. 17)

## 1. Goal
Implement a secure, authenticated self-service account deletion endpoint (`DELETE /api/auth/account`) and an accessible confirmation modal in the dashboard (`components/dashboard/DeleteAccountModal.tsx`) fulfilling GDPR Article 17 (Right to Erasure / "Right to be Forgotten"). The operation requires mandatory re-authentication (password confirmation for credentials users, fresh session check for OAuth users) and rate limiting. On valid deletion, the server purges the user's Supabase Storage objects (`resumes-raw/${user_id}/*`), permanently deletes the user's authentication identity via the Supabase admin client (`supabaseAdmin.auth.admin.deleteUser(user.id)`), which triggers the confirmed PostgreSQL cascade chain, sets `usage_events.user_id` to `NULL` (anonymized telemetry), invalidates active sessions and auth cookies, and returns a clean 200 response.

## 2. Interface Contract
- **API Endpoint:** `DELETE /api/auth/account`
  - **Authentication & Re-Authentication Guard:**
    - Requires active Supabase session via `supabase.auth.getUser()`. Returns `401 Unauthorized` if absent.
    - Mandatory re-authentication payload: `{ "password"?: string }`.
    - For email/password accounts, validates credentials via `supabase.auth.signInWithPassword({ email: user.email, password })` before proceeding. Returns `403 Forbidden` if password verification fails.
    - For OAuth users, verifies session freshness (e.g. `auth_time` within 10 minutes) or requires re-authentication confirmation.
  - **Rate Limiting:**
    - Guarded by IP and user rate limiting (e.g. maximum 3 failed attempts per 15 minutes; maximum 1 deletion request per user).
    - Returns `429 Too Many Requests` when limits are exceeded.
  - **Confirmed Database Cascade Chain (No Schema Migration Needed):**
    - The cascade chain in `supabase/migrations/20261021000000_initial_schema.sql` is confirmed:
      - Line 13: `public.profiles.id` references `auth.users(id) ON DELETE CASCADE`.
      - Line 22: `public.resumes.user_id` references `public.profiles(id) ON DELETE CASCADE`.
      - Line 37: `public.jd_targets.user_id` references `public.profiles(id) ON DELETE CASCADE`.
      - Line 52: `public.entitlements.user_id` references `public.profiles(id) ON DELETE CASCADE`.
      - Line 76: `public.usage_events.user_id` is already nullable with `REFERENCES public.profiles(id) ON DELETE SET NULL`.
    - Deleting the user from `auth.users` automatically cascades through `profiles` down to `resumes`, `jd_targets`, and `entitlements`, and automatically nullifies `usage_events.user_id` without needing an explicit `profiles` delete or any new database migration.
  - **Storage Purge (Explicit Server Purge Required):**
    - Supabase Storage objects are NOT covered by database foreign key cascades and must be purged explicitly.
    - Calls Supabase Storage API using the service-role client to list and delete all objects in the private bucket under prefix `${user.id}/` (e.g., `resumes-raw/${user.id}/*`).
    - *Note on T-020:* Storage bucket `resumes-raw` and `parse_jobs` table are introduced in T-020; storage purge and `parse_jobs` cascade assertions depend on T-020 (or are skipped until T-020 is merged).
  - **Session Invalidation:**
    - Invokes `supabase.auth.signOut()` to clear session cookies (`sb-*-auth-token`).
  - **Response:**
    - `200 OK` with JSON `{ "success": true, "message": "Account and all associated data permanently deleted." }`.
- **Frontend Dialog:** `components/dashboard/DeleteAccountModal.tsx`
  - Mounted in `components/dashboard/DashboardView.tsx` within an explicit "Danger Zone" section.
  - Requires user to:
    1. Enter their account password (for password-based accounts).
    2. Type the word "DELETE" into a confirmation input field.
  - Primary button remains disabled until both confirmation criteria are satisfied.
  - Redirects to `/` upon successful deletion with a brief confirmation message.

     - Deleting `auth.users(id)` cascades through `profiles` (line 13) to delete `resumes` (line 22), `jd_targets` (line 37), and `entitlements` (line 52).
     - Confirms `usage_events.user_id` is updated to `NULL` (`ON DELETE SET NULL`, line 76) without manual intervention.

     - *Conditional T-020 Assertion:* If `parse_jobs` table exists (from T-020), asserts cascade deletion; otherwise marks test skipped pending T-020 merge.

## 7. Human-Only Prerequisites
- **Human Decision Required — Stripe Financial Record Retention:**
  Stripe customer IDs, charges, and invoice records are processed externally by Stripe. Under financial accounting and tax compliance laws, businesses must retain financial transaction records (exact retention period to be confirmed with the owner's accountant or lawyer). GDPR Art. 17(3)(b) expressly permits retaining data necessary for compliance with a legal obligation. The repository owner must confirm their policy decision:
  - *Option 1 (Recommended / Standard Tax Compliance):* Retain transaction receipts, Stripe customer ID, and invoice ledgers in Stripe for statutory tax compliance; delete application database records and unlink user PII.
  - *Option 2 (Aggressive Erasure):* Issue Stripe API calls to redact/delete the Stripe Customer object (`stripe.customers.del(customerId)`), recognizing this may impede historical tax accounting and refund audits.

## 10. Acceptance Criteria
1. **First Test Real Schema Migration:** The test suite's very first test verifies that deleting a user against the real schema (`20261021000000_initial_schema.sql`) cascades cleanly across `profiles` (line 13), `resumes` (line 22), `jd_targets` (line 37), `entitlements` (line 52), and anonymizes `usage_events` with `user_id = NULL` (line 76).
2. **Confirmed No-Migration Architecture:** Explicitly relies on existing PostgreSQL cascade definitions; no new database migrations and no explicit `profiles` delete queries are added.
3. **Strict Cross-User Isolation:** Calling deletion for User A has zero effect on User B's records or storage files.
4. **Re-Authentication Required:** Request fails with `403 Forbidden` unless valid user credentials are confirmed.
5. **Rate Limiting Guard:** Exceeding deletion retry thresholds returns `429 Too Many Requests`.
6. **Explicit Storage Purged:** All uploaded files in Supabase Storage prefixed with `${user.id}/` are explicitly purged using the service role client (conditional on T-020 bucket presence).
7. **Auth Identity Deleted & Cookies Wiped:** `supabaseAdmin.auth.admin.deleteUser(user.id)` is executed and session cookies are cleared.
8. **Typed Modal Confirmation:** UI modal requires typing "DELETE" and entering password before firing request.
9. **No Resume or PII Logging:** Never logs resume content, user email, or passwords to console.
